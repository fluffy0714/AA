# АА: архитектура первого прототипа

## Реализовано

- Адаптивный браузерный интерфейс на HTML/CSS/ES modules; manifest и SVG-иконка.
- Node.js HTTP API без runtime-зависимостей: каталог, расчёт, health.
- Общая доменная модель для серверной и переносимой статической демосборки.
- Два демоадаптера с фиксированными вымышленными товарами, ценами и правилами.
- Корзина в памяти страницы, без localStorage, истории и регулярных покупок.
- Явная маркировка деморежима и запрет реального оформления (HTTP 501).

```text
apps/web/          интерфейс, HTTP-клиент, иллюстрации, manifest
apps/api/          сервер, проверка запросов, ограниченная раздача файлов
packages/domain/   канонический демокаталог, валидация, сравнение
providers/         демоадаптеры; место для будущих официальных интеграций
tests/             финансовые инварианты и HTTP-проверки
scripts/           переносимая статическая сборка
docs/              исследование и план подключения
```

## Контракт и инварианты

Запрос `POST /api/compare`:

```json
{
  "items": [{ "productId": "milk", "quantity": 2 }],
  "regionId": "moscow-center",
  "scenario": "normal",
  "promo": ""
}
```

Цена и поставщик не принимаются от браузера. Количество целое от 1 до 99,
неизвестные и повторяющиеся идентификаторы отклоняются. Размер JSON ограничен.
Все суммы — целые копейки, валюта прототипа RUB. Весовые товары не имитируются:
«1 кг» в демо — фиксированная упаковка. Реальный вес потребует отдельного контракта.

`provider.quote(request, {now})` возвращает идентификатор, статус, строки товаров,
subtotal, discount, delivery, service, surge, total, quotedAt, expiresAt, checkout.
Статусы: `complete`, `incomplete`, `unavailable`. `null` означает неизвестную
сумму и никогда не заменяется на ноль в полном итоге.

Победитель определяется только для двух полных, действующих расчётов. Равенство
цен не объявляет победителя. Цена действительна пять минут. Изменение количества,
района, промокода или сценария сбрасывает старый расчёт; запоздавший HTTP-ответ
не может перезаписать новый. Наличие лишь одного расчёта не доказывает экономию.

В демо соответствия заданы fixtures с `identity`, а не найдены по названиям.
В реальной интеграции нужен серверный каталог соответствий: GTIN при наличии,
бренд, вариант, масса/объём и упаковка. Неточное совпадение потребует согласия
пользователя; оно не должно попадать в автоматическое «точное сравнение».

## Развитие MVP

1. Получить от обоих сервисов подтверждение сценария, спецификацию и sandbox.
2. Выбрать один город и ограниченный ассортимент; верифицировать SKU и упаковки.
3. Добавить адрес/координаты, магазины, временной слот, серверную авторизацию.
4. Реализовать один официальный read-only адаптер и контрактные тесты по sandbox.
5. Добавить второй, таймауты, ограничения частоты, частичные отказы, наблюдаемость.
6. Реализовать передачу корзины/checkout только по подтверждённому контракту.
7. Перед покупкой обновлять quote, требовать подтверждения изменившейся цены,
   использовать идемпотентность. Деньги и заказ не должны дублироваться при retry.
8. Добавить HTTPS-хостинг, защищённое хранение секретов и необходимые операции
   с персональными данными. Провести end-to-end проверки обоих сервисов.

Секреты находятся только на сервере. Статическая сборка — исключительно демо:
её расчёт выполняется в браузере и не пригоден для доверенного оформления.
Это адаптивный web-прототип с manifest, а не завершённая offline PWA: service worker
пока не нужен, чтобы случайно не кэшировать устаревшие цены.
